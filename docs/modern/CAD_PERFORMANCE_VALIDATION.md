# CAD 离线性能验证

本报告记录 2026-09-05 修复工作树上的实测结果。被测源码尚处于集成阶段；这里的数字用于定位剩余瓶颈，不代表发布包验收完成或生产容量承诺。问题基线见 [审计快照](AUDIT_2026-09-05.md)，复现实验的唯一实现为 [benchmark_cad_pipeline.py](../../scripts/benchmark_cad_pipeline.py)。

## 复现方法与隔离

在仓库目录执行：

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
& backend/.venv/Scripts/python.exe scripts/benchmark_cad_pipeline.py --sizes 100 1000 --repeats 3
```

输出为一个 JSON 文档，包含各次采样和中位数。脚本只在专属系统临时目录创建合成 DXF、Excel、任务和空配置，结束后删除自己的目录。导入应用前设置独立环境文件、运行配置、数据库、上传、输出和配置目录；禁止 socket connect，所有模型调用都是内存替身。没有使用真实 API Key，没有调用供应商、DWG 转换或 Windows COM。

本次环境为 Windows 11 10.0.26200、Python 3.12.4，进程可见 24 个逻辑 CPU。计时使用 `perf_counter`；合成图纸均为 R2010、ModelSpace 中的 TEXT，内容为带序号的中文阀门标签。提取包含真实 DXF 读取和 Excel 写入；回填包含真实 DXF 读取、按实体句柄替换和保存，并重新打开产物检查所有译文。图纸生成时间不计入处理耗时。

## 图纸处理实测结果

以下为首次验证，后续列表修复复测也重复了图纸处理；两轮差异只能反映采样和机器负载变化，不能归因为列表代码带来了图纸加速。

| 场景 | 100 个 TEXT | 1000 个 TEXT |
|---|---:|---:|
| 提取并写 Excel，3 次中位数 | 0.0506 s | 0.2545 s |
| 按实体句柄回填 DXF，3 次中位数 | 0.0229 s | 0.1078 s |
| 两个独立提取任务顺序完成，一次采样 | 0.2402 s | 0.6002 s |
| 两个独立提取任务并行完成，一次采样 | 0.1369 s | 0.6664 s |

100 个 TEXT 的首次提取为 0.3930 s，后两次为 0.0504 / 0.0506 s，说明库首次使用和系统缓存影响明显。1000 个 TEXT 三次提取为 0.2545 / 0.2365 / 0.3049 s。不能只报热路径最快值。

两任务并行使用同一 `CADPipelineService` 和两个工作线程，检查各任务 ID 独立且记录数正确。1000 个 TEXT 并行比顺序更慢，说明解除注册锁阻塞后，Python/Excel 和文件 I/O 阶段仍受本机资源竞争影响；增加线程数不能保证加速。此处没有真实慢 COM 阶段，因此这些计时不能单独证明慢转换不会阻塞其他任务，锁范围还需由并发回归测试证明。

### 历史列表

用独立元数据目录建立已完成任务；请求页大小固定为 100。冷读指清空应用摘要缓存后的第一次调用，不表示操作系统磁盘缓存也被清空。热读连续采样 3 次，任务内容不变。

| 历史任务数 | 冷读一次 | 热读中位数 | 热读各次采样 |
|---|---:|---:|---|
| 100 | 0.8064 s | 0.0158 s | 0.0261 / 0.0158 / 0.0158 s |
| 1000 | 8.5374 s | 0.1701 s | 0.1714 / 0.1558 / 0.1701 s |

### 原子快照读优化后的复测

列表读不再对每条 JSON 获取写锁；写入方用原子替换发布完整元数据，列表允许读取旧或新完整快照，以文件签名在下次轮询失效缓存。坏记录及目录与 manifest ID 不符的记录跳过。采用相同默认命令重新测量：

| 历史数 | 原先冷读 | 优化后冷读 | 原先热读中位数 | 优化后热读中位数 |
|---|---:|---:|---:|---:|
| 100 | 0.8064 s | 0.3529 s | 0.0158 s | 0.0082 s |
| 1000 | 8.5374 s | 3.0740 s | 0.1701 s | 0.0805 s |

优化后 1000 条热读三次为 0.0805 / 0.0811 / 0.0797 s。该修改确实降低列表锁开销，但两轮均非独占机器、冷样本各一次，不能把全部差值精确归因为单一代码变化。

另以独立命令测量 10000 条历史，避免生成无关的 10000 实体图纸：

```powershell
& backend/.venv/Scripts/python.exe scripts/benchmark_cad_pipeline.py --sizes 100 --history-sizes 10000 --repeats 1
```

| 历史数 | 原子快照读冷样本 | 随后的热样本 | 返回条数 |
|---|---:|---:|---:|
| 10000 | 51.9782 s | 3.1177 s | 100 |

**该轮验证暴露的性能边界：** 当时 `task_page` 调用 `list_tasks` 全量遍历、stat、缓存/读取摘要并排序后分页。1000 条冷读已改善，但约 3 秒仍可感知；10000 条冷读接近 52 秒、后续一次热读超过 3 秒，不能据此宣布大历史量交互已达标。当时摘要缓存最多 5000 项，对稳定顺序遍历 10000 项且逐 miss FIFO 淘汰会发生缓存抖动；操作系统文件缓存仍可使第二轮更快，不能仅从墙钟耗时推断应用缓存命中。冷样本没有清除操作系统缓存，也没有控制系统文件扫描器，所以需保留测量条件，不将其描述为固定磁盘极限。

这组数据促成了后续可重建索引改动。分页参数本身不等于按页索引查询，新增索引的结果见下节。

列表优化后的同轮图纸复测：100 / 1000 个 TEXT 提取中位数为 0.0386 / 0.1892 s，实体回填为 0.0157 / 0.0876 s；两个 1000 TEXT 任务顺序 0.5250 s、并行 0.5063 s。结合首次并行更慢的结果，仍不足以支持提高并发数。probe 0.1008 s 且只调用一次，限流与取消断言继续通过。

### 可重建 SQLite 摘要索引验证

当前正常列表使用 SQL `LIMIT/OFFSET`，规范任务保存同时更新摘要索引，删除移除对应项；JSON manifest 仍为可恢复的权威数据。启动会校验目录和文件签名，导入旧记录并检查活跃任务的执行者。性能验证因此必须分开计算一次性旧数据导入、启动校验、首个列表请求和后续列表请求，不能把启动成本藏到计时区间外后统称为冷启动耗时。

复现命令：

```powershell
& backend/.venv/Scripts/python.exe scripts/benchmark_cad_pipeline.py --sizes 100 --history-sizes 100 1000 10000 --repeats 3
```

每个规模使用独立元数据目录。先建立没有索引的旧 manifest，计时首次 reconciliation；然后创建新的服务实例，计时 `recover_interrupted_jobs` 执行的启动校验，再单独计时第一页和最后一页。旧记录均为已完成任务，因此启动校验数字不包含大量活跃任务恢复。末页使用偏移量 `history_count - 100`，不是始终取首页。

| 历史数 | 首次导入，序列读取基线 | 重启校验 | 重启校验后的第一页 | 后续末页中位数 | 单次规范保存 JSON + 索引中位数 |
|---|---:|---:|---:|---:|---:|
| 100 | 0.1434 s | 0.0211 s | 0.00361 s | 0.00364 s | 0.00941 s |
| 1000 | 4.7723 s | 0.1178 s | 0.00397 s | 0.00409 s | 0.00988 s |
| 10000 | 48.7073 s | 1.0995 s | 0.00424 s | 0.00496 s | 0.00778 s |

首次导入、启动校验、首个请求各一次，后续页和保存各 3 次。保存走 `_save_task`，包含任务生命周期锁、JSON 原子发布和 SQLite 更新，不是只测裸 SQL insert。生成所有旧 fixture 文件的时间不计入首次导入；第一次索引创建和旧数据读取计入。

10000 条常规页查询由上轮约 3.118 s 降至约 0.005 s，解除每次列表重新读取历史 manifest 的问题。代价是首次导入和每次重启校验仍有与历史量相关的成本，不能将这两个成本写成零。索引正确性、跨进程更新、损坏重建和并发删除需由主回归套件证明，本脚本证明的是上述合成规模的性能和返回数量。

为进一步降低首次迁移成本，当前导入最多使用 8 个文件读取线程，每批最多 128 条，SQLite 写入仍在同一事务中顺序执行。对 10000 历史按 `--sizes 100 --history-sizes 10000 --repeats 1` 重新独立采样：

| 指标 | 序列导入基线 | 有界并行导入后 |
|---|---:|---:|
| 首次旧 manifest 导入 | 48.7073 s | 9.9765 s |
| 重启签名校验 | 1.0995 s | 1.4794 s |
| 重启校验后的第一页 | 0.00424 s | 0.00480 s |
| 后续末页 | 0.00496 s（三次中位数） | 0.00598 s（一次） |
| 规范 JSON + 索引保存 | 0.00778 s（三次中位数） | 0.01070 s（一次） |

首次旧数据导入下降到约 10 秒；常规页仍在约 5–6 毫秒。启动仍需约 1.5 秒签名校验，首次从无索引升级仍需等待迁移完成。序列和并行基线并非同一时刻运行，无法排除系统负载、文件缓存和扫描器影响，因此保留绝对采样值，不承诺固定倍数。新版脚本还验证一次规范保存后的字段更新确实出现在索引页中，防止把无效保存计作写入性能。

### LLM 离线调度

| 验证项 | 实测或断言结果 |
|---|---|
| 同候选两个并发 probe；模拟网络延迟 0.1 s | 总计 0.1011 s，只调用一次模拟网络，两个结果均成功 |
| 容量 1、每秒补充 1 token、同一单调时刻连续申请 4 次 | 返回预订延迟 `[0, 1, 2, 3]` 秒 |
| 100 个文本 chunk、并行上限 2；第二个调用启动时取消 | 仅启动 2 个替身调用，取消异常向调用者传递 |

审计快照中的旧 probe 实验为 5.109 s；本轮相同 0.1 s 模拟延迟的并发实验已不再等待那个超时窗口。token bucket 返回值是确定性时钟下的配额预订结果，不是四次真实 HTTP 的时间戳。取消实验覆盖停止提交新 chunk；已进入供应商的 HTTP 调用能否马上终止不在此证据范围内。

独立执行已有 LLM 回归套件：

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD='1'
& backend/.venv/Scripts/python.exe -m pytest tests/backend/test_llm_audit_regressions.py -q -p no:cacheprovider
```

结果为 **16 passed in 1.22s**。这组测试还覆盖异常 probe 唤醒、凭据变更失效、漏项响应拒绝、取消重试和代理配置。它不替代整个后端、前端或发布套件。

## 可据此采取的架构取舍

保留单体及有界工作池。已实测的全量列表读取推动引入可重建摘要索引，常规页面查询达到毫秒级；首次旧记录导入和启动签名校验仍需单独计入部署/启动等待。再依据真实图纸分别测量转换、提取、翻译和回填阶段。对于 CPU/Excel 密集处理，当前两线程实测不支持继续提高并发数；供应商网络等待占主导时需另行根据实际配额测试。没有真实 DWG、复杂块/属性/字体、大体积图纸、真实供应商限额及错误率的数据，本报告不推算生产 TPS、峰值并发、费用或所谓最佳线程数。
